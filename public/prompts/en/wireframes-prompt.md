Based on the PRD document, create **simple Wireframes (Low-Fidelity)** for **all of the product’s screens, each screen exactly once**, as a single image named **wireframes.png**.

**What counts as a screen:**

- A screen is a separate page or view that the user navigates to in the application.
- Different states of the same screen (for example empty, loading, error, success, or long content), messages, pop-ups, and the same screen shown in another language **are not separate screens**.
- Show each screen **exactly once**, in its normal, representative state and in the primary interface language defined in the PRD. Do not show versions, variations, or additional states of the same screen.

**Before creating the image:**

- In your reply, write a numbered list of the product’s screens (the name of each screen) and their total count, and then immediately create the image, without waiting for approval.
- The image must contain **exactly the screens in the list**, no more and no fewer. The list appears in the text of your reply only, not inside the image.

**Guidelines:**

- Identify from the PRD the screens, the User Flows, and the user’s primary actions.
- Use the User Flows to determine which screens are required and how to arrange them, **but do not display flow diagrams, arrows, notes, or textual explanations about the flow itself in the image**.
- In each screen, show only the required UI components, such as: headings, buttons, input fields, menus, lists, cards, content areas, and navigation elements, according to the PRD.
- Display **the screen name above each screen in the interface language defined in the PRD**, identical to the name in the list.
- Maintain a clear hierarchy, a logical screen structure, and consistent navigation across the screens.
- Adapt the Wireframes to the platform, device type, screen size, language direction (RTL / LTR), and interface language, as defined in the PRD.
- Use a **Low-Fidelity** style only: black, white, and shades of gray only, with no colors, no final visual design, no final images, and no decorative visual elements.
- Do not add features, screens, states, or components that do not appear in the PRD. If a small detail is missing that is necessary to understand the screen structure, you may add only a minimal and reasonable UI component, without adding new functionality.
- Arrange the screens according to the order of use or the user’s main flow, so that the logical progression between them is clear.
- Arrange all screens on a single board using a Grid Layout, with uniform spacing between the screens. **The number of screens determines the layout, not the other way around:** do not add screens, copies, or variations to fill or balance the image. Choose the number of rows and columns according to the number of screens and their dimensions, so that the overall image is balanced, compact, and readable. Prefer an overall aspect ratio close to a square or a balanced rectangle, and only where possible also close to the golden ratio (1.618:1). When there are many screens, avoid a layout that is excessively long in a single row or a single column; when there are few screens (for example 1–3), they may be arranged in a single row, and empty space around them is acceptable. Maintain a uniform and readable size for all screens.
- Only when the product is intended for mobile, present the Wireframes inside frames with a realistic smartphone aspect ratio, such as 9:19.5. Keep all screens at consistent dimensions, and avoid creating screens that are excessively long or disproportionately tall. If the content is longer than the screen height, show only the visible area (Viewport) and imply that scrolling is possible, instead of extending the frame.
- Maintain high readability of the screens and their components, and do not compress the layout at the expense of clarity.
- Do not add a general title for the board, screen numbering, a legend, decorative frames, arrows, or any text that is not part of the Wireframes themselves.

**Goal:**  
To illustrate the screen structure, the placement of components, and the relationship between the screens, before the visual design stage.

**Required Output:**  
- One image only, named **wireframes.png**, containing exactly the screens in the list, each screen once.
- Do not add User Flows, notes, explanations, or any text that is not part of the Wireframes themselves.
