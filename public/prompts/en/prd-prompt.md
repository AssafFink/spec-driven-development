I would like to create a **PRD.md** document describing a system I intend to build.

Ask me questions, one at a time, and wait for my response before moving on to the next question, in order to gather the information needed to create the document.

All questions and the final PRD document must be written in English. However, all user-facing UI text, such as headings, buttons, messages, and labels, must use the interface language defined for the product, regardless of the document language.

**Process Guidelines:**
- Ask only relevant and meaningful questions necessary to understand the product, users, needs, features, and scope.
- Do not ask questions that have already been answered in the conversation.
- When appropriate, present several options to choose from, with a brief explanation of each.
- Do not invent requirements, features, or information that have not been defined. If essential information is missing, ask me about it. If an assumption is needed for a non-essential detail, explicitly label it as an assumption.
- Focus on product requirements and known constraints, without selecting technologies, frameworks, or architecture unless explicitly specified.
- Once enough information has been gathered to create a clear and complete PRD, stop asking questions and proceed to generate the document.

**At the end of the process, create a file named PRD.md in Markdown format, following the structure below:**

### 1. Background and Objectives
a. **Product Purpose:** Describe the product's purpose in one sentence.

b. **Problem Statement:** Describe the problem or user need that the product is intended to address.

c. **Proposed Solution:** Explain how the product solves the problem or addresses the need.

### 2. Target Audience and User Needs
a. **User Personas:** Briefly define the primary users, their profiles, and their characteristics.

b. **User Stories:** Briefly describe user actions from the user's perspective, using the following format:

"As a [type of user], I want to [perform an action], so that I can [achieve a benefit]."

### 3. User Flows and Experience
a. **User Journey:** Describe what the user is trying to achieve and in what context, from the initial need to achieving their goal.

b. **User Flows:** Describe the sequence of screens and actions the user goes through to complete a specific task.

c. **UX Requirements:** Define the UX principles the product must follow.

### 4. Functional Requirements
a. **Features & Functional Requirements:** List the product's features and detail the functional requirements of each, including the necessary business rules and expected behavior.

b. **Edge Cases & Error Handling:** Describe relevant edge cases and how the system should handle them.

### 5. Technical Requirements and Constraints
a. **Technical Requirements:** Define the platforms on which the product must operate, such as Web, Mobile, Desktop, operating systems, browsers, interface languages, and similar requirements.

b. **Constraints:** Define known requirements and limitations, such as security, privacy, budget, external integrations, and similar considerations.

### 6. Out of Scope
a. **Out of Scope:** Provide a clear list of features or components that will not be included in the current version of the product.

---

**Final Document Guidelines:**

- The document must be clear, concise, and well-structured, without unnecessary repetition.
- Include only information and sections relevant to the product.
- Ensure consistency between requirements, User Stories, and User Flows.
- Do not add features or requirements that were not approved during the conversation.
- The document must be sufficiently detailed to serve as a foundation for further planning, design, and development of the system using AI.
